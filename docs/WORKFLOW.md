# 从需求到上线：工作流程

这份文档记录这几个项目（GoEuroOps、Vparser、个人主页）一个需求从提出到上线的做法，包括每一步做什么、为什么这样做，以及踩过的坑。三个仓库各放一份，内容相同。

文档里不写任何密码、口令、内测码或服务器地址：它们只存在服务器的 `.env` 和网关配置里。

---

## 总览

```
理解需求 → 查清现状 → 定方案（大改动先确认） → 实现 → 本地测试与预览 → 上线 → 线上验证 → 提交推送 → 汇报
```

每一步都要有证据：测试输出、截图或 curl 结果。「应该没问题」不算完成。

---

## 1. 理解需求

- **先弄清想要什么效果，再决定怎么做。** 比如「更高级」可能是给 HR 看，也可能是想要艺术感，两种做法完全不同。拿不准时先问，或者先给参考、给预览，而不是直接大改。
- **只问真正需要对方拍板的事。** 能从代码、现状或常识推断出来的，就直接做，并在汇报里说明做了什么选择。需要问的，通常是这几类：
  - 删除数据；
  - 公开隐私信息（例如简历上的手机号）；
  - 花钱；
  - 在几个方向明显不同的方案里选一个。
- **长期约束要一直记着**，每次改动都要检查一遍：
  - 网站不放电话号码，不放公司内部的用户量这类敏感数字；
  - 本地和 GitHub 上的默认行为保持原样，只有公开演示服务器才开启的功能（如内测码、额度），一律用环境变量打开；
  - 不引入新的前端依赖，字体只用系统字体（Google Fonts 在国内常被阻断）；
  - 所有界面文案都要有中、英、瑞三语。
- **用户中途追加的要求**，在当前任务中顺带处理，不要搁置到最后忘掉。

## 2. 查清现状

改之前先把现状摸清楚，避免建立在错误的假设上：

- 读相关代码，找到可以复用的函数和已有的写法，而不是另起一套。
- 查线上的真实状态：
  - 服务器资源：内存、对公网开放的端口；
  - 数据：现在有哪些账号；
  - 配置：模型单价等参数是否真的生效。

  例如这次查到模型单价配置成了 0，说明花费统计从来没有生效，这直接影响了方案。
- 查外部事实时要找一手来源。比如模型价格去官网价格页查，不凭记忆。

## 3. 定方案

- **小改动**（改文案、修 bug、调样式）：直接做。
- **大改动**（改版、新功能、涉及服务器）：先写计划，给用户确认后再动手。计划要写明：
  - 为什么改：背景和目标；
  - 改哪些文件、复用哪些现有代码；
  - 风险和取舍，例如「会不会被攻击」这类问题要正面回答；
  - 怎么验证。
- **优先选改动小、可回退的做法。** 例如：
  - 花费统计通过 gRPC 元数据带上用户 ID，不改接口定义；
  - 服务器状态面板只写一个静态 JSON 文件，不开新端口。
- **新功能默认关闭，用环境变量打开**，本地开发的行为保持不变。

## 4. 实现

- 代码风格跟周围代码保持一致：注释多少、命名习惯、写法都照着来。
- 新逻辑配新测试。例如花费上限要覆盖这些情况：
  - 没到上限、刚好到上限；
  - 不限额的用户；
  - 上限为 0 时关闭检查；
  - Redis 不可用时不能把演示站拖垮。
- 前端文案写成三语，错误提示按错误码翻译，不直接把服务端的中文原文显示给英文用户。
- 给不同的错误分配专门的错误码，例如 40301 表示「需要内测码」，42901 表示「额度用完」，不和通用的 403、429 混用。

## 5. 本地测试与预览

- 跑全部测试：
  - server-go：`go test ./...`
  - agent-py：`uv run python -m pytest`
  - 前端：`npm test && npm run build`
- 页面改动用无头 Chrome 截图检查：
  - 桌面（1440 宽）和手机（390 宽）；
  - 深色和浅色；
  - 中、英、瑞三语；
  - 有开场动画的，截一张动画刚开始时的画面；
  - 依赖线上数据的部分，用模拟数据在本地先调好样式。
- 截图要逐张看，不只看「命令成功了」。很多问题只有看图才发现，例如点云被名字挡住、代码块太窄被截断、深色模式下按钮太亮。
- 设计类改动先给用户本地预览地址或截图，确认后再上线。

## 6. 上线

服务器内存只有 1.6 GB，所以原则是：**不在服务器上编译，只传本机做好的成品；只重启改动过的服务。**

| 项目 | 上线方式 |
|---|---|
| 个人主页 | 运行 `./deploy/publish.sh`：给 CSS、JS 地址加内容指纹 → 写入构建信息 → rsync 到服务器。不需要重启任何服务 |
| GoEuroOps 前端 | 本机 `npm run build` → 把 `dist/` 传到服务器 → 基于原镜像构建覆盖层（`FROM goeuroops-frontend:latest` + 替换静态文件）→ `docker compose up -d --no-build frontend` |
| Vparser | 本机交叉编译 server-go（`GOOS=linux GOARCH=amd64`）、编译前端、准备 agent-py 的 `app/` → 分别基于原镜像构建覆盖层 → 只重建改动过的容器 |

- **配置改动**：
  - 应用配置：先备份 `.env` 再修改，然后重建对应容器；
  - 网关配置：先备份站点文件再修改，然后运行 `caddy reload`，不中断服务。
- **数据改动**：先 `mysqldump` 备份。密码在本机用项目自己的哈希函数算好再写入，明文不落库。
- **覆盖层的边界**：只改了代码时可以用覆盖层。改了依赖（`go.mod`、`package.json`、Python 包）就必须在本机完整构建 amd64 镜像，再用 `docker save | ssh docker load` 传到服务器。
- **权限系统拦下的操作**，不要换个写法绕过去。先把能做的做完，再向用户说明要做什么、为什么需要，让用户授权或自己执行。

## 7. 线上验证

上线后必须在线上实测，不能以「本地通过」代替：

- 用 curl 走一遍真实请求，正常情况和被拦截的情况都要测。例如：
  - 注册：没有内测码被拒、填错被拒；
  - 登录：演示账号能登录；
  - 计费：追问一次后计数增加；把额度临时设为用完，请求被拒，测完恢复原值；
  - 密码：新密码能登录，旧密码失效。
- 用无头 Chrome 截线上页面。
- 确认同一台服务器上的其他站点没有受影响（个人主页、GoEuroOps、Vparser 都要检查）。
- 检查资源占用：用 `free -m` 看内存，用 systemd 看新服务的内存占用。

## 8. 提交、推送、汇报

- 提交说明写清楚「改了什么、为什么」。一个提交只做一件事；上线时自动更新的指纹和构建信息，单独提交。
- 推送到 GitHub，服务器上的仓库也 `git pull` 到同一个版本。
- 汇报内容：
  - 做了什么；
  - 怎么验证的，附具体结果；
  - 中途出过什么问题、怎么修的，如实说明，包括自己造成的问题；
  - 还剩什么需要用户处理，并给出现成的命令。

## 踩过的坑

| 问题 | 原因 | 现在的做法 |
|---|---|---|
| 用户看到页面「排版全乱」，我的截图却正常 | CSS、JS 被浏览器缓存 1 小时，新页面用上了旧样式；无头浏览器每次都是全新的，没有缓存 | 资源地址加内容指纹；判断设计效果时，也要考虑有缓存的回访用户会看到什么 |
| 发布脚本把英文简介那一行替换坏了 | 写构建信息的正则 `build [^<]*<` 太宽，匹配到了「I build …」 | 正则锚定到 `class="build-id"`；发布后用 curl 检查关键文字 |
| 构建号总带着「+」 | 脚本先写指纹，再检查工作区是否干净 | 在修改任何文件之前记录 commit 状态 |
| 密码哈希写进数据库后损坏 | 哈希里的 `$` 被远程 shell 当成变量展开 | 含特殊字符的值用 base64 传递，写入后立即登录验证 |
| 高程数据很糊 | Mapzen 地形瓦片在北纬 60° 以上用的是低精度数据 | 换用 Copernicus GLO-30（30 米） |
| 在服务器上构建镜像导致 SSH 卡死 | 内存只有 1.6 GB | 在本机构建，服务器只做覆盖层 |
| 误点了删除按钮，浏览器弹出确认框，自动化卡住 | 用自动化脚本点击页面时没有避开危险按钮 | 截图脚本自动关闭弹窗，并避开删除类按钮 |

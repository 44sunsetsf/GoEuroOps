# 2026-10 改动记录

## 1. 工具层重构：统一网关、Pydantic 定义、金额护栏、只读 MCP 入口（2026-10-01）

### 问题
- 两套工具抽象并存：13 个 Agent 工具只有白名单和手写的简化校验，缓存、超时、熔断、降级只落在检索这一个工具上。
- 参数校验是手写的，不支持嵌套（报价的 `items` 数组要靠函数自己检查），返回值完全没有校验。
- "金额只能由工具算"只靠工具说明和提示词约束，线上没有拦截；trace 只在内存里保留最近 200 条。
- `mcp/` 目录并不是 MCP 协议，名字有误导，还占用了官方 SDK 的包名。

### 改动
| 改动 | 位置 |
|---|---|
| `mcp/` 改名 `retrieval/`，`MCPToolManager` 改名 `RetrievalManager` | `retrieval/` |
| 熔断器抽成共用模块 | `tooling/breaker.py` |
| 全部 Agent 工具的入参改用 Pydantic 定义；发给模型的 JSON Schema 由模型生成（内联 `$ref`、折叠 Optional） | `tooling/schemas.py`、`agents/tools.py` |
| 报价、退款的返回值模型检查业务不变量；不满足就不把结果交给模型 | `tooling/schemas.py` |
| 工具网关：每个工具声明超时、副作用类型、是否熔断、结果上限；同步函数放线程执行 | `tooling/gateway.py` |
| 结果过大时截断列表并标 `truncated`、`truncated_lists` | `tooling/gateway.py` |
| 金额护栏：流式按句放行，没有依据的金额所在句被替换；`GOEUROOPS_AMOUNT_GUARD` 三档 | `tooling/amount_guard.py`、`agents/agent_orchestrator.py` |
| 工具指标和 `/tools/stats` | `core/metrics.py`、`api/main.py` |
| 只读工具的 MCP 入口（FastMCP），依赖单独装 | `mcp_server.py`、`requirements-mcp.txt` |

### 验证
- 测试 140 → 165：网关（超时、熔断、异常隔离、返回值校验、截断、统计）、嵌套参数校验、
  金额护栏（抽取、替换、流式、放行有依据的金额）、Agent 端到端（编造总价被拦、工具算出的金额放行、
  非法参数回传给模型）、MCP 协议往返。
- 护栏关掉（`off`）后端到端的两个护栏测试会失败，说明测试确实在检查护栏。
- 金额依据集合每次请求多花约 0.26 ms。

### 没做
- 输入侧用 `tool_choice` 强制先调用报价工具：当前模型服务是 DeepSeek 的 Anthropic 兼容接口，对 `tool_choice` 的支持没有验证过。
- trace 落盘和审计、请求整体时间预算、`create_consultation_lead` 的幂等键：下一步。

## 2. 记忆模块按 A-Mem 思路重写，只保留一种记忆（2026-10-06）

### 问题
- 记忆叠了五层：Redis 工作记忆、会话摘要、情景记忆（摘要向量）、逐句索引、用户画像，再加一个可切换的 A-Mem 魔改笔记层（`GOEUROOPS_MEMORY_IMPL`），两套实现、两个开关，每层都要单独提炼或压缩。
- 记忆的向量用的是 ChromaDB 默认的英文 MiniLM，中文几乎没有区分度：压力题里问“我现在每年的预算是多少”，三句讲预算的话一句都没取回，取回的全是闲聊。
- ChromaDB 带过滤条件的查询偶尔报 “Cannot return the results in a contigious 2D array”，原来这时整次检索返回空，模型看不到任何记忆。
- 自建 30 题所有方案都是 100%，分不出好坏。

### 改动
| 改动 | 位置 |
|---|---|
| 只剩一种记忆：最近 14 条原文（Redis 滑动窗口，不调模型）+ A-Mem 笔记（ChromaDB） | `memory/amem.py` |
| 用户的每句陈述立刻存成原文笔记；同一句话再说只刷新时间 | `memory/amem.py` |
| 一次模型调用批量补全：关键词、标签、背景、事件时间、关键事实字段、链接、取代；时机是攒够 8 句、换了会话、或用户空闲 2 分钟 | `memory/amem.py` |
| 演化只追加：旧背景进 versions 并重算向量，被取代的笔记标“后来有更新” | `memory/amem.py` |
| 关键事实不再单独维护画像，从笔记的字段汇总：单值字段以最新为准、旧值留档，经历和偏好列出全部 | `memory/amem.py` |
| 向量模型和知识库共用 bge-small-zh，查询带检索指令编码 | `memory/amem.py` |
| 向量查询报错时，在这位用户的笔记里精确计算距离 | `memory/amem.py` |
| 后台任务保留引用；关闭服务时取消空闲计时、最多等 5 秒 | `memory/amem.py`、`api/routes/chat.py` |
| 删除旧实现和两个开关；旧代码在分支 `backup/memory-v2-and-amem-modded`、tag `memory-legacy-backup` | `memory/`、`docker-compose.yml`、`.env.example` |
| 新增 10 道压力题：闲聊陈述也会存成笔记（含干扰项）、多会话、反复修改、相对时间、多跳 | `evaluation/memory_benchmark.py` |

## 3. 记忆模块：A-Mem 笔记之上加客服分层（2026-10-13）

### 问题
- 记忆只有用户说过的原话，助手答应的事（“周四晚上 8 点视频”“顾问明天把选校清单发你邮箱”）回访时找不回来。
- 身份证号、护照号会被原样存成笔记，用户一问就答出来。
- “删除我的资料”只生成交接单，记忆、对话记录都删不掉；笔记永久保存。
- 转顾问的交接单只有最后一句话，顾问要自己翻聊天记录。
- 关键事实由模型标在笔记上、读取时临时汇总，顾问没法核实或改正。

### 改动
| 改动 | 位置 |
|---|---|
| 分层：会话状态（Redis）、客户档案、咨询记录、原话笔记（A-Mem，沿用原集合） | `memory/manager.py` |
| 客户档案：字段带出处原话、说话时间、来源和历史；合并规则由代码决定（后说的为准、晚到的旧说法只进历史）；顾问核实过的字段模型不能改，用户的不同说法记为待核实 | `memory/profile.py` |
| 咨询记录：会话停下来（空闲 2 分钟或换会话）后写摘要，含没解决的事和约好的下一步；同一会话接着聊时在原摘要上增量更新 | `memory/cases.py` |
| 一次模型调用同时补全笔记、抽档案候选、写咨询记录 | `memory/consolidate.py` |
| 证件号写入前就换成占位符，任何一层都不存 | `business/lead_store.py::redact_sensitive_ids` |
| 顾问接口：看档案、改字段、隐私删除（清会话、档案、咨询记录、笔记、后台对话记录） | `api/routes/memory.py`、`core/chat_log.py::forget` |
| 笔记保留 180 天，过期的在整理时删除 | `memory/notes.py` |
| 交接单附上客户档案和以前的咨询记录（线索面板的 background） | `agents/tools.py` |
| 提示词里档案标“用户自述，未核实；付款、订单、报价以系统查询结果为准”；超出字数预算先裁最早的笔记 | `memory/manager.py` |
| 新增 8 道客服题；评测可以选实现，便于新旧同题对比 | `evaluation/memory_benchmark.py`、`evaluation/locomo_benchmark.py` |

### 验证
模型 deepseek-v4-pro（和之前用 flash 的报告不能直接比），新旧版用同一套题，自建题各 3 次，LoCoMo 3 次。

| | 旧版 A-Mem | 纯分层（去掉 A-Mem 链接，未采用） | **新版：分层 + A-Mem 笔记** |
|---|---|---|---|
| 基础 + 难题 30 题 | 100% | 100% | **100%** |
| 压力题 10 题 | 100% | 100% | **100%** |
| 客服题 8 题 | 50% | 100% | **100%** |
| LoCoMo 70 题 | 51 / 41 / 44，平均 45.3% | 43 / 37（2 次） | **53 / 47 / 47，平均 49.0%** |
| 维护 token（30 题每次） | 2.3 万 | 5.4 万 | 6.3 万 |

- 纯分层版把原话只按原文算向量、不顺链接扩展，LoCoMo 取回的证据变少；说明在线上的中文向量模型上，A-Mem 的补全和链接对检索有用。所以保留 A-Mem 笔记做检索层，只把客服能力叠在上面。
- 旧版在客服题上丢的 4 题：助手约好的时间、顾问的承诺（只出现在助手回复里），以及护照号、身份证号被记住。
- 代价：整理要多写咨询记录，维护 token 约为原来的 2.5 倍。
- 测试：`tests/test_memory.py` 取代 `tests/test_amem.py`，全部后端测试 199 个通过。

### 没做
- 已有用户的关键事实不迁移到档案：线上是演示站，旧笔记照样能检索，档案从下一次整理开始积累。
- 前端还没有档案面板，顾问接口先用 API 调。
- 删除请求不删线索和交接单（业务记录，由顾问在线索面板处理），也还没有删除审计记录。

## 4. 可靠性：参考 EchoMind 2026-09/10 的修复（2026-10-15）

### 问题
对照原项目 EchoMind 最近三次更新，逐条核对 GoEuroOps 的代码，以下几处它已修好、我们还没有：
- 熔断器半开时放行所有请求，注释写的“放行一次探测”并没有做到；熔断前发出的慢请求返回成功，会把刚打开的熔断器关上。
- 每类 Agent 只有一个实例，监控惩罚只在同类实例之间择优，等于不影响路由；惩罚还按进程启动以来的累计成功率计算，很久以前的故障会一直拖着。
- 专属 Agent 失败改由 GeneralAgent 回答时，失败那次的工具轨迹被覆盖；流式输出时，失败前已经流出的半段文字和新回答拼在一起。
- Judge 评分失败按 0.5 计入均分、通过率和回归对比，一次超时就可能误报回归，还会被存成基线；缺字段时也悄悄补 0.5。换了用例的评测也和基线比。
- 评测用的是线上编排器：转顾问用例会在站长的线索库里生成交接单，评测流量也会进监控统计。
- 知识库降级结果被当成检索成功交给模型；`knowledge_used` 只要调用过检索工具就为真，查空也算。

### 改动
| 改动 | 位置 |
|---|---|
| 熔断器改成 ticket 机制：半开只放一个探测，旧 ticket 的结果忽略，探测丢失 60 秒后再放一个 | `tooling/breaker.py`、`tooling/gateway.py`、`retrieval/manager.py` |
| Agent 统计加最近 50 次调用的窗口；路由惩罚按最近 5 分钟、至少 5 次的成功率和首字耗时计算 | `agents/base.py`、`monitor/performance_monitor.py` |
| 咨询、费用 Agent 惩罚达到 0.5 时本次路由交给 GeneralAgent，`routing_reason` 记 `monitor_fallback`；窗口清空后自动恢复 | `agents/agent_orchestrator.py` |
| 回退时保留两次的工具轨迹，插一条 `agent_fallback`；已经流出文字时先发 SSE `reset`，前端清空 | `agents/agent_orchestrator.py`、`api/routes/chat.py`、前端 `backends.js`、`App.vue`、`ChatPanel.vue` |
| Judge 输出严格校验（空、截断、JSON、缺字段、布尔、NaN、越界），最多试两次，401/403 不重试；失败的样本不计分 | `evaluation/evaluator.py` |
| 报告加 `status`、`scored`、`judge_failed`、`suite_id`；只有完整报告才做回归对比、更新基线，回归只在同一套件之间比 | `evaluation/evaluator.py`、`api/routes/evals.py`、前端评测页 |
| 评测用单独的编排器，线索写内存 | `api/main.py` |
| 检索降级条目不进合并结果，全部降级时返回失败；`knowledge_used` 只在真的查到内容时为真 | `retrieval/manager.py`、`api/routes/chat.py` |

### 验证
- 后端测试 199 → 221，新增 `tests/test_reliability.py`：半开只放一个探测、旧结果不能关熔断、探测丢失后重放；降级 Agent 被跳过且原因可查、窗口清空后恢复、单纯变慢不触发；回退的事件顺序（token → reset → token）和轨迹合并；Judge 的 6 种坏输出、重试和鉴权不重试；部分失败的报告不进均分、不覆盖基线；不同套件不比回归；检索降级返回失败。
- 前端构建通过。

### 没做
- EchoMind 的请求幂等（`client_request_id` + Redis 事务回执）：我们只有一个后端进程，前端也不自动重试，收益小。
- 异步评测任务、Bearer Token 角色鉴权、标准 MCP 客户端：前两项等商业化，最后一项留学咨询用不上。
- 旧基线没有 `suite_id`，上线后第一次完整评测只建基线、不报回归。

## 5. 知识库：文档生命周期 + 检索评测基线（2026-10-15）

### 问题
- 同一篇上传文档改了内容再导入，**旧版本删不掉**：片段 ID 是“来源 + 标题 + 序号 + 正文前 50 字”的哈希，内容一变就成了新增。实测新旧两版同时留在库里，检索时旧版分数（0.576）还略高于新版（0.567）；旧片段里的金额还会被金额护栏当成“有出处”。
- 种子更新是**先删后写**：线上向量走 API，重启时 API 恰好不可用，知识库会被清空到下次重启。
- 没有删除和按文档列出的接口。
- 没有检索评测集，切块、阈值、重排的改动都没法量化。

### 改动
| 改动 | 位置 |
|---|---|
| 每篇文档有 `doc_id`（可指定，默认“来源 + 标题”）和内容版本 `doc_version`；再导入时没变就跳过，变了先写新版、成功后删旧版 | `retrieval/knowledge_base.py` |
| 种子逐篇增量同步；全部写成功后才删业务目录里已没有的种子和早期示例文档（早期示例里也有“退款政策”这个标题，按版本而不是按标题判断） | `retrieval/knowledge_base.py` |
| 启动时给旧片段补 `doc_id`（只改元数据），之后按文档替换和删除 | `retrieval/knowledge_base.py` |
| `GET /knowledge/documents`、`DELETE /knowledge/documents/{doc_id}`；`/knowledge/add` 可传 `doc_id` | `api/routes/knowledge.py`、`api/schemas.py` |
| 检索评测集 106 条：普通、口语、专有名词、跨领域干扰、多轮追问、超出服务范围、知识库里没有答案；脚本在临时目录新建知识库，走线上的门控链路 | `evaluation/datasets/retrieval_v1.jsonl`、`evaluation/retrieval_benchmark.py` |

### 验证
- 新增 `tests/test_knowledge_base.py`（9 个）：改内容再导入只剩新版、内容不变不重复向量化、块数变少删多余、向量化失败保留旧版、指定 `doc_id` 可以改标题、种子增删改、种子同步失败保留旧种子、删除和列表、旧片段补 `doc_id` 后可被替换。后端测试 221 → 230。
- 检索基线（本地 bge-small-zh，45 个片段，门控 Top-3、分数下限 0.4）：

| 指标 | 基线 |
|---|---|
| Hit@1 / Hit@3 / MRR（93 条有答案） | 76.3% / 97.9% / 0.867 |
| 注入命中（过阈值后真正给到 Agent） | 90.3% |
| 专有名词 Hit@1 | 57.1% |
| 无答案误注入率（13 条） | **53.8%** |
| 平均每次注入 | 766 字 |

- 结论：召回不是瓶颈（Hit@3 接近 98%），问题在**排序精度**（Hit@1 只有 76%）和**阈值没有区分度**（一半无答案的问题也被注入了片段）。这两项是下一步重排要解决的。
- 这一步不改检索行为，改完后重跑基准，数字和基线完全一致。

## 6. 知识库检索：重排换成 bge-reranker、预取也重排、追问补全（2026-10-15）

### 问题
在第 5 节的评测集上，**用线上同款向量模型（bge-large API）**重测基线，暴露出本地 bge-small 看不到的问题：
- 0.4 的混合分阈值在线上太高：正确文档排进前 3 的有 95.7%，真正注入给 Agent 的只有 **67.7%**；同时无答案问题有 23.1% 被注入。混合分对“相关 / 不相关”没有区分度。
- 预取链路不重排；深查用大模型逐条打分，多一次 LLM 调用，分数也不稳定。
- “那德国呢”这类追问，预取只用当前这句，注入命中只有 33.3%。

### 改动
| 改动 | 位置 |
|---|---|
| 重排改成调 bge-reranker-v2-m3 的 API（和向量 API 共用密钥）；失败、超时、熔断时退回混合分 | `retrieval/rerank.py`、`retrieval/manager.py` |
| 预取也重排（和意图识别并行，延迟被藏住）；深查删掉大模型逐条打分 | `retrieval/manager.py` |
| 阈值按分数来源区分：重排分 ≥ 0.1，未重排时混合分 ≥ 0.4 | `retrieval/rerank.py`、`core/rag_gate.py` |
| 检索结果同一文档只留得分最高的一块，不重复占 Top-K | `retrieval/knowledge_base.py` |
| 短追问拼上上一轮用户的话再预取；深查改写和重排也参考上一轮 | `core/rag_gate.py`、`agents/agent_orchestrator.py`、`agents/tools.py`、`retrieval/manager.py` |
| 评测脚本按线上方式做追问补全（`--no-followup` 做对照），报告逐条记录最高分，用来校准阈值 | `evaluation/retrieval_benchmark.py` |

### 验证（线上同款模型：bge-large-zh 向量 + bge-reranker-v2-m3，在后端容器里用临时目录建库）

| 指标 | 改前 | 改后 |
|---|---|---|
| 预取 Hit@1 / Hit@3 / MRR（93 条有答案） | 83.9% / 95.7% / 0.900 | **91.4% / 97.9% / 0.944** |
| 预取注入命中 | 67.7% | **85.0%** |
| 追问的注入命中（6 条） | 33.3% | **100%** |
| 无答案误注入（13 条） | 23.1% | **15.4%** |
| 深查 Hit@3（改写 + 重排） | 72.0%（大模型逐条打分） | **83.9%**（少一次大模型调用） |
| 深查对无答案问题返回片段 | 0% | 15.4%（变差：大模型打分对无关结果更严） |

- 测试 230 → 238：重排排序与降级、熔断、两种阈值、预取按重排分过滤、深查按补全后的问题重排、追问补全的边界（换话题、长句不拼）、同一文档只留一块。
- 单次检索的耗时从约 180 ms 变成约 1 秒，主要是重排接口的网络往返（服务器在新加坡，接口在国内）。预取和意图识别（一两秒）并行，基本被藏住；深查少了一次大模型调用，整体更快。

### 试过、没合入
- **按结构切块 + 块间重叠 + 命中后返回整篇**：在同一组线上对照里，新切块是 Hit@1 92.5%、Hit@3 96.8%、误注入 23.1%，旧切块（500 字）是 91.4%、97.9%、15.4%。没有可测量的提升，返回整篇还让每次注入从 476 字涨到 832 字。原因是文档都很短（最长约 1200 字），每块又带着标题。按“没有提升就不合入”的规则撤回；以后接入长手册时再评估。
- **重排分和混合分双信号阈值**：两种分数在有答案和无答案问题上的分布都重叠，双信号最多多保住 1 个点，不值得增加规则。
- **BM25 独立召回**：Hit@3 已经 97.9%，召回不是瓶颈。
